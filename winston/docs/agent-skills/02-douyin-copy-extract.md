# 从需求到技能：抖音口播文案提取

## 需求的起源

我做短视频口播，日常需要大量参考文案。刷到好的，以前的操作是：复制、切窗口、粘贴进备忘录、记一句"这条钩子不错"。一个星期下来备忘录里躺着几十条，再也没有然后。

痛点很明确：**收藏的动作比收藏的价值大**。存的时候觉得捡到宝，用的时候永远想不起存过。

## 需求定义

我把需求写成了一句可以验收的话：

> 给我一个抖音链接，三十秒内，把口播文案原文、开头钩子、内容结构、可复用套路拆出来，归档进我的素材库。

拆开看，这里有几个明确的子任务：拿原文、拆结构、抽套路、归档。每一步都能单独验证，这就是个好需求。对比一下模糊版本"帮我分析这个视频"——没法验收，AI 只能瞎猜。

## 流程设计

Skill 的执行流程是这样的：

1. **输入校验**：是链接还是已复制的文本？链接能不能打开？打不开就直接报错，不硬猜
2. **内容提取**：优先拿口播原文，拿不到标题和话题标签兜底，并在结果里标明来源可信度
3. **结构拆解**：按"钩子—观点—案例—行动号召"拆段，这是口播内容的标准骨架
4. **套路提炼**：这条视频真正可复用的东西是什么？一句话说清，说不清就写"无明显套路"，不硬编
5. **归档**：按预设字段写入素材库，附上来源链接和提取日期

第 4 步是关键。拆结构是体力活，提炼套路才是这个 Skill 的灵魂——它决定我下次写文案时能不能真的用上这条素材。

## 踩过的坑

**坑一：什么都想拆。** 第一版把完播率、互动率、发布时间全分析一遍。跑了一个月发现，那些数据对我写文案毫无帮助，还拖慢了速度。删掉之后，从三十秒变成十秒。教训：Skill 的字段越少，被调用的概率越高。

**坑二：归档格式随心所欲。** 早期字段时有时无，检索起来想撞墙。后来固定成模板，宁可字段留空，不许结构漂移。AI 员工也要考勤制度。

**坑三：过度信任提取结果。** 有几次拿到的"原文"其实是视频简介， Skill 没标来源，我照着写了段子，发出去才发现文不对题。后来加了来源可信度标记，低可信度的结果必须人工过目。**Skill 可以草率，我不能。**

## 效果与边界

现在这个技能每周稳定调用十几次，素材库从"备忘录坟场"变成了真正的参考库。写文案卡壳的时候，按套路检索，一分钟能找到三条可复用的结构。

它的边界也很清楚：只拆结构，不代写；只归档，不评判。创意那部分，是我的活儿。
